# 認証ありYTMusicの取得元・照合実験

## 方針

推薦の主な取得元はYTMusicの曲ラジオと関連曲とする。MusicBrainzは
必要になった場合の録音・メタデータ識別補助で、今回の取得には使っていない。
ジャンルは当面優先しない。Appleのgenre IDとの対応は未解明で、
ジャンルフィルターを外す実験設定の実アプリ・iPodでの受け入れも未確認。

取得結果の順序はAppleのGenius rankとは別に保存する。
曲名・アーティスト・長さによる一致は候補で、同じ録音という確定ではない。
ライブ、リミックス、伴奏などの版表記を削除して同一視しない。

## 保存済み結果の再集計

「ツバサグラビティ」の2回分について、取得時の照合候補を数えた。
1回目は旧照合方法、2回目は長さを考慮する方法のため、照合数の差を
推薦の変動だけに帰属させることはできない。

| 項目 | 1回目 | 2回目 |
| --- | ---: | ---: |
| 観測行 | 70 | 70 |
| radio行 | 50 | 50 |
| related行 | 20 | 20 |
| ユニークvideo ID | 65 | 66 |
| 種曲以外でローカル候補があるvideo ID | 11 | 7 |

両回に共通するvideo IDは56、和集合は75。
この結果ではアカウント認証成功を証明できていない。

## 10曲の実験準備

`scripts/probe_ytmusic_batch.py`を追加した。

- ローカルライブラリからアーティスト表記とアルバム表記が重ならない10曲を選ぶ。
  曲数の多いアーティストを優先するため、無作為標本ではない。
  Off Vocal / instrumental / カラオケの明示表記は種曲から除外する。
- アカウント情報APIでアカウント項目が確認できたときだけ検索・推薦取得へ進む。
  アカウント名・画像・ハンドルは保存しない。
- HTTP request呼び出しの開始間隔は既定5秒、1回の実行で最大45呼び出し。
  タイムアウトは25秒。エラーはその実行を停止し、自動再試行しない。
  これはサービスの許容上限を確認した値ではなく、この実験の自己制限。
- 検索はsongsを指定し、曲名・アーティスト・長さでvideo ID候補が1つに
  絞れた場合だけ収集する。それでも録音の同一性はunverifiedのまま。
- 成功したAPI応答は許可した曲情報のフィールドだけキャッシュする。
  同じ実験ディレクトリでの再実行では成功済みの問い合わせを再送しない。
  キャッシュの取得日時を保持し、推薦を再観測したいときは別ディレクトリを使う。
- `--plan-only`ならネットワークを使わず種曲一覧だけ作成できる。

種曲一覧はignoredな `data/ytmusic/coverage-01/seeds.json`に保存した。
元LibraryとGenius DBへの書き込みはない。

## 実行結果と残る条件

最初の実行はネットワーク制限でConnectionErrorとなった。
制限外での実行ではget_account_infoがKeyErrorとなり、検索前に停止した。
個人情報を出さない診断でaccount/account_menuのHTTP 200応答を確認したが、
accountNameとactiveAccountHeaderRendererは存在しなかった。
multiPageMenuRenderer等は存在した。

このため現在のbrowser.jsonでログイン状態を確認できない。
期限切れと応答形式変更のどちらかはこの証拠だけでは断定しない。
新規の曲検索・推薦データは取得していない。認証情報を更新して再確認することが
次の条件で、引き続き欠落する場合はaccount APIの形式を調べる。

19テストのうち15件が成功、提供Musicバイナリが必要な4件は通常設定でスキップ。
追加テストは、認証応答欠落時の停止、秘密フィールドを保存しないキャッシュ再利用、
種曲のアーティスト・アルバム分散を検証した。

## 追加ヘッダーによる認証成功と取得結果

ユーザーから新しいブラウザーのリクエストヘッダーが提供された。
最初に主要Cookieだけで作ったJSONではアカウントを確認できず、
ログイン補助Cookieを追加した後に通常のytmusicapiでget_account_infoが成功した。
どの補助Cookieが必要だったかは個別に検証していない。
前節の失敗を、そのまま元JSONの期限切れと断定する根拠にはしない。
ブラウザーの静的署名とクライアントバージョンを使う比較も実施したが、
最終的な取得はytmusicapi標準の署名更新で成功している。

認証JSONはignoredなdata配下、権限0600に保存した。
Cookie・署名・アカウント情報はリポジトリや調査記録に記載しない。
以前置かれていたbrowser.jsonは変更していない。

### 10曲の検索

英語設定と日本語設定を別々のディレクトリで比較した。
それぞれ認証確認1回と検索10回、合計11回のHTTP呼び出しで完了し、
レート制限エラーは観測していない。一般的な利用上限が判明したという意味ではない。

英語設定では、10曲すべてが現行の厳密照合では未解決となった。
主な問題は曲名への英訳追加、アーティストのローマ字表記、
複数アーティストのローカル文字列とリモート配列の違い、アーティスト項目の欠落。
最初の検索結果の9曲は長さの差が0.030〜0.842秒だったが、
長さの近さだけでは同一録音を確定しない。
一部には異なるアルバム版もあり、Game Size / Off Vocal / 年版 / 歌唱者版を
削除する照合は採用していない。

日本語設定ではytmusicapiのsearchが10曲とも空配列を返した。
元の応答を保存していないため、検索自体の空結果とパーサーの問題は未確定。
当面の既定言語は英語のままとし、日本語を選ぶ場合は別保存先を用いる。
言語をmanifestに含め、同じ保存先での言語変更は拒否する。

保存済み検索結果から、10曲のローカル情報・検索候補・長さ差を一覧化した
`data/ytmusic/coverage-01/match-review.json`も作成した。
これは候補のレビュー用で、自動確定やGenius DB書き込みには使っていない。

### 既選択の種曲による対照取得

以前に選択した「ツバサグラビティ」のvideo IDを使い、
アカウント確認後にラジオ・関連曲を取得した。
4回のHTTP呼び出しで成功し、結果を
`data/ytmusic/tsubasa-authenticated-03.json`に保存した。

- 観測70行: radio 50、related 20。
- 種曲以外は69行、ユニークvideo ID 65。
- ローカル照合候補があるvideo IDは7。
- 対応するローカルPIDは8。1つの観測は候補PIDが複数あり未解決。
- 候補のローカルアーティスト表記は4種類、アルバム表記は5種類。
- 録音の同一性が確認できた件数は0。種曲自体も既選択の候補として扱う。

これにより認証ありの推薦取得自体は動作した。
次の課題は、翻訳併記・アーティスト別名・複数クレジットを保持した対応表を作り、
確認した曲だけをローカル推薦グラフに取り込むこと。
10曲の一括対応と互換DB生成が完了したという結果ではない。

### 取得制限の補強と検証

サブエージェントのオフラインレビューで、requestsの自動リダイレクトが
件数・間隔制御を迂回すること、NaNの間隔指定が待機を無効化することを確認した。
自動リダイレクトを無効化して3xxは停止し、非有限の間隔指定も拒否するよう修正した。
追加のオフラインテストでリダイレクト、間隔、件数上限、タイムアウト、
NaN/無限大の拒否を確認した。全22テスト中18件成功、バイナリ統合4件はスキップ。
