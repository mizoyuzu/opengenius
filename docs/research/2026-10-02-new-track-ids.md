# metadataの再選択間隔と新規Genius ID

## 選曲コアでの新規ID実験

元の7フィルターを保ったまま、合成した新規Genius IDと32バイトmetadataを
MusicのARM64選曲コアへ渡した。ジャンルIDは元metadataで最も多い値29を使い、
それがindex 0のジャンル適合map内に存在することを先に確認する。
残る3つのIDは合成した同一性グループであり、実曲の属性IDとして認定したものではない。

| 合成条件 | 利用可能曲数 | コアが返した曲数 |
| --- | --- | --- |
| index 1〜3がすべて曲ごとに異なる | 6 | 6 |
| index 1だけ全曲で同じ | 6 | 1（seedのみ） |
| index 2だけ全曲で同じ | 6 | 1（seedのみ） |
| index 3だけ全曲で同じ | 6 | 1（seedのみ） |
| index 1〜3がすべて曲ごとに異なる | 30 | 30 |

`probe_genius_metadata.py`で再現できる。合成metadata、曲存在確認、履歴0、時刻0、
固定seed乱数を使う実験であり、Music.app全体やiPodの受け入れ確認ではない。
既存6曲に限らず新規IDでも選曲コアが処理できることと、
同一性グループの割り当てが選曲を止める条件になり得ることを確認した。

## distanceは同じIDを再選択するまでの間隔

型3の4パラメータは、静的解析と実命令を使う状態テストで次の役割を確認した。

| パラメータ | 意味 | 既存設定 |
| --- | --- | --- |
| p0 | metadata配列のindex | 1、2、3 |
| p1 | 間隔しきい値を緩めるときの下限 | 2、2、3 |
| p2 | 最初のしきい値 | 6、10、10 |
| p3 | 最初に足す乱数の範囲（0〜p3-1） | 6、6、6 |

0x10036715cは、選択したmetadata IDのカウンターを1に戻し、
それ以外のIDのカウンターを1増やす。これは累計の出現頻度ではなく、
最後に選んでからの経過を追う状態である。
0x1003670bcは`threshold > age`なら拒否値1を返す。
未出現のIDや`age >= threshold`の場合は0となる。

状態テストではA→Bと選ぶとA=2、B=1になり、再びAを選ぶとA=1、B=2に戻った。
しきい値は0x100367128で6→5→4→3→2と緩み、2で止まった。
Aのage=2、threshold=6では拒否され、threshold=2では拒否されなかった。
しきい値の初期化0x100367580では、base 6と固定乱数3から9になることも確認した。

ageが選択直後に1になるため、しきい値2は少なくとも別IDの選択を1回挟む条件になる。
同じIDしか候補にない場合、p1まで緩めても新しい曲を選べない。
既存の6曲のように属性グループが偏った候補群では、関係列があっても選曲が成立しない。

## index 1〜3の属性名はまだ仮説

提供6曲のmetadataとローカルタグを比較したところ、全36組のペアで
以下の同値関係が一致した。

- index 1が等しい ⇔ artist文字列が等しい（2グループ）。
- index 2が等しい ⇔ album文字列が等しい（3グループ）。
- index 3が等しい ⇔ title文字列が等しい（6グループ）。

このサンプルではartist／album／曲のグループという解釈が整合する。
ただし6曲だけの相関なので、別バージョン・カバー・コンピレーション等での
一般的な意味や、AppleのIDとローカルタグをどう対応させるかは確定していない。
自動的にタグをIDへ変換して本番metadataを書き出す実装はまだ行っていない。
個人の照合表は`data/genius-metadata-local-correlations.json`に保存した。

## Library.musicdbの新規ID保存

提供ファイルで再現できた保存条件は以下だった。

- hfmaヘッダーは160バイト。u32@8とu32@128は総ファイル長。
- 圧縮はzlib level 1。元の展開データを再圧縮すると圧縮streamが全バイト一致した。
- u32@84の102,400バイトを上限として、16バイト境界までのprefixをAES-128-ECBで暗号化する。
  圧縮streamの残りはそのまま保存する。AES鍵は既存decoderと同じ。
- 925件のitmaヘッダーはすべて376バイト。Genius IDを保存するスロットはLE u32@+0xCC。

`rewrite_music_ids.py`は未対応曲のこの4バイトだけを変更し、別ファイルへ保存する。
最初に無変更の再エンコードが元Libraryと完全一致することを要求する。
変更後も展開データの差分が指定したスロットだけであることを確認し、
ヘッダーでは総長2箇所以外を保持する。再エンコード後の復号・展開・曲の照合も行う。
未知ヘッダーフィールドの意味は未確定で、Music.appがそれらを検証するかは未確認。

指定JSONの形式（IDとハッシュは例、実際の値へ置き換える）:

```json
{
  "schema_version": 1,
  "source_library_sha256": "元Library.musicdbのSHA-256",
  "assignments": [
    {
      "persistent_id": "0000000000000011",
      "genius_id": "0000000070000001"
    }
  ]
}
```

対象PIDが存在し、既存Genius IDが0であることを要求する。
Genius IDは非ゼロuint32、他の曲と衝突しない値だけを許可する。
既存IDの置き換え、未知PID、重複、元Libraryハッシュの違い、
既存出力や原本ディレクトリへの書き込みは拒否する。

未対応の6曲に実験用IDを付けたコピーを
`data/Library-genius-id-experiment.musicdb`へ生成した。925曲のままで、
展開後の差分は6スロットのみ。IDを持つ曲は6曲から12曲になった。
これはLibrary側の保存だけの実験で、Genius DBへ新しいmetadata／関係行を追加していない。
そのため、このコピーをGenius化済み・そのまま使用可能とは扱わない。
最終対象ライブラリと原本は変更していない。

## 検証と残る実装

実バイナリの状態テスト1件と、Libraryの再エンコード／ID制約テスト2件を追加し、
バイナリ統合テストを有効にした全16件が成功した。
合成metadataの5ケースと、実Libraryの無変更再エンコード・6スロット変更も確認した。

次の実装は、同じ曲に対してLibraryのIDとGenius DBのmetadata／関係行を一緒に生成し、
相互参照と選曲結果を検証すること。
metadataの属性対応を仮定する実験と、意味が確定した互換生成は区別して進める。
Music.appでの読み込みと純正iPodの同期形式・受け入れは、引き続き別の検証が必要。
